# 0108 — AX 코치: 오늘 무엇을 하면 실증 자료가 쌓이는가

> 성과 화면(`/performance`)은 **이미 나온 결과**를 봅니다. AX 코치(`/ax-coach`)는
> **지금 무엇을 해야 결과가 생기는지**를 알려 줍니다. 둘을 겹치지 않게 둡니다.
>
> 이 문서는 「이렇게 하면 좋겠습니다」가 아니라 **지금 코드가 이렇게 합니다**입니다.

## 0. 한 줄

사용법 안내가 아닙니다. **지금 실증에서 어느 증거가 비었는지 세어 보고, 그 증거를
만들어 낼 「원래 해야 하는 실제 업무」를 골라 주고, 그 업무가 실제로 일어났는지를
기존 기록으로 확인합니다.**

```
실제 업무기록 수집 → 네 갈래 준비도 계산 → 비어 있는 갈래 찾기
   → 그 갈래를 채울 오늘 할 수 있는 실제 업무 고르기 → 쉬운 말로 제시
   → 사용자가 원래 하던 업무 수행 → 실제 기록 발생 여부 확인
   → 준비도 갱신 → 다음 일 재선정 → 7·14일 리포트
```

## 1. 절대 규칙 — 「완료」 단추가 없습니다

화면에 있는 단추는 **「업무하러 가기」 하나**입니다 (`수거 입력으로` · `통장 입금
대사로` · `주문 보기` · `거래처 보기` · `오늘 일정으로`).

| 누른 것 | 시스템이 하는 일 |
|---|---|
| 업무하러 가기 | 「오늘 이 일을 받았다」는 **발행 사실**만 기록하고 업무 화면으로 이동 |
| (완료 단추) | **없습니다** |

다 했다는 판정은 `verifyMission()` 이 **기존 업무 기록**을 보고 합니다.
발행 시각 **뒤에** 생긴 기록만 봅니다 — 그러지 않으면 예전 기록이 오늘 한 일처럼
셉니다. 발행 기록이 없으면 오늘 0시부터 봅니다.

| 일 | 무엇을 보고 확인하나 | 종류 |
|---|---|---|
| 오늘 수거 바로 입력 | `collection_events` 수거 완료 (취소·시연 제외) + 다녀온 날 = 입력한 날 | 새 기록 |
| 입력이 빠진 방문 채우기 | 그 `schedule_id` 의 수거 완료 이벤트 | 새 기록 |
| 병원이 포털로 직접 요청 | `client_requests.source = 'portal'` 또는 `product_orders.source = 'portal'` | 새 기록 |
| 주문 전달까지 | 그 주문의 `delivered_at` | 새 기록 |
| 입금 맞추기 | 그 청구의 `paid_at` (취소 아님) | 새 기록 |
| 오늘 업무 마감 | `day_closes` 오늘 행 | 새 기록 |
| 전달 자재 기록 | `materials` 행 또는 수거 이벤트의 `material_ids` | 새 기록 |
| 거래처 기본정보 | 그 거래처의 주소·전화가 비어 있지 않음 | 상태 변화 |

**포털 요청은 병원이 올린 것만 셉니다.** 직원이 대신 접수한 요청(`source='staff'`)으로는
확인되지 않습니다 — 그러면 증거를 직원이 만들어 내게 됩니다.

발행 이력에 `verified_at` 이 적혀 있어도 **화면은 믿지 않습니다.** 열 때마다 실제
기록으로 다시 확인합니다. 그 칸은 「그때 무엇을 보고 확인했나」를 되짚기 위한
메모입니다. (`check_axcoach` ⑫ · `check_coachui` ⓔ 가 이것을 못 박습니다)

## 2. 실증 자료 준비도 (`src/lib/axCoach.ts` → `coverageOf`)

**새로 세는 숫자가 하나도 없습니다.** `axEvidence()` 와 `evidenceSample()` 이 낸 값을
목표와 견주기만 합니다. 목표값도 새로 정하지 않고 기존 상수를 그대로 씁니다 —
`BREADTH_RULE`(30건·14일·5곳·2명·80%) 과 `AX_MIN_SAMPLES`(5).

| 갈래 (화면 이름) | 항목 | 목표 | 출처 |
|---|---|---|---|
| **업무 활용** | 현장에서 입력한 수거 | 30건 | `evidenceSample().field` |
| | 입력한 날 | 14일 | breadth.operatingDays |
| | 다녀온 일정을 입력한 비율 | 80% | breadth.coverage |
| | 입력이 끝난 수거 | 5건 | `workAx.entered` |
| **매출 증거** | 소모품 주문 | 5건 | `salesAx.orders` |
| | 실제 전달 완료 | 5건 | `salesAx.deliveredOrders` |
| | 청구까지 확정 | 1건 | `salesAx.billedRevenue.samples` |
| | 입금까지 완료 | 1건 | `salesAx.paidRevenue.samples` |
| | 두 번 이상 산 병원 | 1곳 | `salesAx.repeatBuyers` |
| **운영 확장** | 완료한 방문 | 30건 | `capacityAx.visits` |
| | 실제 나간 날 | 14일 | `capacityAx.activeDays` |
| | 기사별로 셀 수 있는 사람 | 2명 | `capacityAx.drivers` |
| | 차량 운행일당 수거량을 잰 날 | 5일 | `capacityAx.kgPerVehicleDay.samples` |
| **병원 직접사용** | 병원이 직접 올린 요청·주문 | 5건 | `customerAx.portalRequests + portalOrders` |
| | 포털을 쓴 병원 | 2곳 | `customerAx.portalClients` |
| | 두 번 이상 쓴 병원 | 1곳 | `customerAx.repeatPortalClients` |
| | 접수 → 처리 시간을 잰 건 | 5건 | `customerAx.responseHours.samples` |

전체 준비도는 **네 갈래의 평균**입니다. 네 문장은 같은 무게라 한 갈래가 다 찼다고
나머지를 메울 수 없습니다.

**주문 ≠ 매출 ≠ 입금.** 네 단계를 한 칸에 합치지 않습니다 (매출 증거의 네 항목).

**못 센 것(`null`)과 0 을 가릅니다.** 값이 `null` 인 항목은 화면에 「아직 못 셈」이라고
나오고, 0 인 항목은 「0건」으로 나옵니다. 진행률로는 둘 다 0 이지만 읽는 사람에게는
다른 말입니다.

### ⚠ 준비도는 성과가 아닙니다
「자료가 얼마나 모였는가」입니다. 46% 는 46% 좋아졌다는 뜻이 아니고, 화면에도
그 문장이 숫자 바로 아래 붙습니다. 「실증 준비 상태」(`/readiness`, 서류까지 포함한
대표님 점검표)와 이름이 비슷하므로 이 화면에서는 **「실증 자료 준비도」**라고
부릅니다.

## 3. 오늘 할 일 고르기 (`missionCandidates`)

**데이터에 실제 대상이 있을 때만 후보가 됩니다.** 전달 안 된 주문이 없으면 전달
미션은 아예 만들지 않습니다 — 할 수 없는 일을 시키면 그다음부터 아무도 안 봅니다.

```
우선순위 = 갈래 부족도 × 이 일이 채우는 양 × 오늘 실행 가능성 × 업무 중요도
```

| 일 | 언제 뜨나 | 갈래 | 역할 |
|---|---|---|---|
| 오늘 수거 바로 입력 | 오늘 예정이고 아직 완료 안 된 방문이 있을 때 | 업무 활용 | 전원 |
| 입력이 빠진 방문 채우기 | 완료 표시만 있고 수거 입력이 없는 일정이 있을 때 (이관 자료 제외) | 업무 활용 | 전원 |
| 병원이 포털로 직접 요청 | 포털 기록이 목표에 못 미칠 때 | 병원 직접사용 | 관리자·사무실 |
| 주문 전달까지 | 전달 안 된 주문이 실제로 있을 때 | 매출 증거 | 관리자·사무실 |
| 입금 맞추기 | 미입금 청구가 실제로 있을 때 | 매출 증거 | 관리자·사무실 |
| 오늘 업무 마감 | 오늘 완료한 수거가 있는데 마감 기록이 없을 때 (판 106 이상) | 운영 확장 | 전원 |
| 전달 자재 기록 | 최근 7일 수거는 있는데 자재 공급 기록이 없을 때 | 업무 활용 | 전원 |
| 거래처 기본정보 | 오늘 방문하는 병원의 주소·전화가 비어 있을 때 | 업무 활용 | 관리자·사무실 |

- **한 번에 최대 3개.** 많으면 실패입니다.
- **역할이 열 수 없는 화면의 일은 아예 안 보냅니다** — 기사님에게 주문·입금 일을
  띄우면 눌러도 「권한 없음」이 뜨는 막다른 길이 됩니다.
- 같은 일을 **이틀 넘게 발행만 하고 못 채우면** 우선순위를 0.6배로 내립니다. 매일
  같은 카드가 맨 위에 있으면 화면을 아예 안 보게 됩니다. 목록에서 지우지는 않습니다.
- **발행된 일은 오늘의 대상이 사라져도 카드가 남습니다.** 오늘 갈 곳을 다 다녀오면
  후보에서는 빠지는데, 그때 카드까지 없어지면 「✓ 확인했어요」를 볼 자리가 사라집니다 —
  그것을 보려고 화면에 돌아오는 것인데도. (구현 중 실제로 발견한 결함입니다)

## 4. 새 표 — 하나뿐입니다 (`ax_coach_missions`)

준비도·리포트·확인은 전부 **이미 있는 기록**으로 그 자리에서 계산합니다. 그래서
그 값들을 다시 저장하는 표는 만들지 않았습니다 (AX_EVIDENCE_ROADMAP 규칙 5).

다만 「언제 · 누구에게 · 어떤 일이 발행됐는가」는 업무 데이터 어디에도 없는 **새
사실**이라 그것만 남깁니다.

| 칸 | 무엇 |
|---|---|
| `mission_key` · `evidence_area` | 어떤 일인가 |
| `issued_on` · `issued_at` · `issued_by` · `issued_name` · `issued_role` | 언제 누구에게 |
| `target_id` | 대상이 정해진 일이면 그 **기존 기록**의 id (복사 아님, 가리키기만) |
| `verified_at` · `verified_what` | 무엇을 보고 확인했는지 (메모 — 판정의 근거가 아님) |

- 같은 사람·같은 날·같은 일은 **한 번만** (유일 색인). 화면을 여러 번 열었다고
  「발행 5건」이 되지 않습니다.
- RLS: 직원 전원 읽기 · 본인 것만 발행 · 확인 메모만 수정 · **삭제 정책 없음**.
- SQL: `supabase/proposals/PROPOSAL_0108_ax_coach.sql` (판 106 → 108). 대표님이 실행.
- **이 표가 없어도 화면은 그대로 돌아갑니다.** 그때는 「오늘 0시부터」로 확인하고,
  완료 건수를 0 이 아니라 「표가 아직 없어 세지 못했습니다」로 적습니다.

## 5. 최근 7일 / 14일 (`coachReport`)

실제 일어난 것만 셉니다 — 실제 업무를 한 날 · 수거 완료 · 현장에서 입력한 수거 ·
병원이 직접 올린 요청·주문 · 상품 전달 완료 · 입금까지 끝난 청구.

준비도 변화(`31% → 46%`)는 저장해 둔 값이 아니라 **같은 계산을 그 날짜까지로 끊어서**
그 자리에서 다시 냅니다. 기간 전체가 실증 시작일보다 앞이면 「기록 없음」입니다 —
0 이라고 적지 않습니다.

그리고 세 줄: 이번에 새로 확인된 것 · 아직 부족한 것 · 다음 기간에 먼저 채울 갈래 둘.

  오늘 할 일이 없으면 그 줄도 없습니다.
- 갈래를 펼치면 「성과 화면에서 이 칸 자세히 보기」로 그 갈래의 상세(`#ax-work` ·
  `#ax-sales` · `#ax-capacity` · `#ax-customer`)로 갑니다 — **결과는 여기 겹쳐 적지
  않습니다.** 성과 화면이 안 열리는 기사님에게는 이 줄도 없습니다.

거래처 100곳 · 일정 5,200건 · 자재 1,200건 · 주문 40건 · 1년 (AX_EVIDENCE_ROADMAP §3-3 과 같은 규모):

| 무엇 | 처음 | 두 번째부터 |
|---|---|---|
| `axEvidence` (기존) | 211ms | — |
| `coverageOf` (혼자 부를 때) | 192ms | **0ms** |

첫 화면 한 줄 · 코치 화면 · 7일 리포트가 **같은 기간**을 각자 세고 있었습니다

`WeakMap` 에 담아 같은 계산을 두 번 하지 않습니다. 자료를 다시 읽으면 `data` 가
새 객체가 되어 저절로 버려집니다 — 값을 저장해 두는 것이 아닙니다.
