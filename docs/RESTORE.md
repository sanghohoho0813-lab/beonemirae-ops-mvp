# 복구 절차서 — 시스템이 사라졌을 때 되살리는 법

㈜비원미래 운영 시스템 · 처음 실측 2026-08-15(판 52) · 다시 실측 2026-11-10(판 64 + proposals 15개)

---

## 0. 먼저 알아야 할 것

이 문서는 **실제로 되돌려 보고** 쓴 것입니다. 격리된 데이터베이스에서 처음부터 끝까지
해 봤고, 원본과 복구본의 금액이 1원까지 같은 것을 확인했습니다(98개 + 51개 항목).
운영 중인 Supabase 프로젝트에는 손대지 않았습니다.

> ### ⚠ 지금은 무료 플랜입니다 — **자동 백업이 없습니다**
>
> Supabase 의 일 단위 자동 백업은 **유료(Pro) 플랜부터**입니다. 무료 플랜에서는 아래 표의 1번이 **없습니다.**
> 그래서 지금 회사의 백업은 **설정 화면에서 내려받는 전체 스냅샷 하나뿐**입니다(2번).
> 한 달 넘게 안 받으면 관리자 첫 화면에 한 줄이 뜹니다.

| 순서 | 방법 | 되살아나는 것 | 언제 쓰나 | 무료 플랜 |
| --- | --- | --- | --- | --- |
| 1 | **Supabase 백업 복원** | 계정까지 전부 | 실수로 지웠다 · 데이터가 망가졌다 | **없음** (유료부터) |
| 2 | **전체 스냅샷(.json)** | 업무 자료 전부 (계정 제외) | 프로젝트 자체가 사라졌다 · 무료 플랜의 모든 경우 | 있음 |

유료 플랜이어도 1번만 믿으면 안 됩니다 — Supabase 백업은 **그 프로젝트 안에** 있습니다.
결제가 끊기거나, 프로젝트를 지우거나, 계정에 문제가 생기면 백업도 같이 사라집니다.

### 「일시정지」는 사고가 아닙니다 — 복구 절차를 쓰지 않습니다

무료 프로젝트는 1주일 동안 사용이 없으면 **일시정지**됩니다. 화면에 「서버가 일시정지 상태입니다」가 뜹니다.
이때는 **자료도 계정도 그대로** 있습니다. Supabase 대시보드 → 그 프로젝트 → **Restore project** 를 누르면
몇 분 뒤 그대로 돌아옵니다. 이 문서의 복구 절차(스냅샷 붓기)는 필요 없습니다.
다만 일시정지된 채 오래 두면 그 버튼으로 되살릴 수 없게 됩니다(기한은 Supabase 정책에 따릅니다 — 공식 문서 기준으로
90일에서 1년 사이로 바뀌어 왔으니, 일시정지 안내 메일 · 대시보드의 안내를 확인하세요). 미루지 말고 바로 켜 주세요. 일시정지를 막는 방법은 `docs/SERVER_KEEPALIVE_0151.md` 에 있습니다.

## 1. 평소에 해 둘 일 (한 달에 한 번, 5분)

1. 관리자로 로그인 → **설정** 화면
2. 「전체 스냅샷 받기 (.json)」 누르기
3. 받은 파일을 **회사 컴퓨터가 아닌 곳**에 둡니다 (개인 구글드라이브 · 외장하드 등)
4. 화면에 「못 읽은 표 N개」가 뜨면 그건 **반쪽 백업**입니다. 그대로 두지 말고 알려 주세요.
5. 「담지 못한 사본 — 사업계획서 …」가 뜨면, 받은 계정이 사업계획서 참여자가 아니라서입니다.
   참여자인 계정(대표님)으로 받으면 담깁니다.

받은 날은 화면에 남습니다 — 스냅샷 카드의 「마지막으로 받은 날 … (n일 전)」.

파일 이름에 날짜와 시각이 들어 있어(`비원미래-전체스냅샷-20260815-0930.json`)
같은 날 두 번 받아도 서로 덮어쓰지 않습니다.

> 같은 화면의 **CSV** 는 백업이 아닙니다. 사람이 엑셀에서 검산·제출하는 용도입니다.
> CSV 는 거래처를 이름으로 적기 때문에, 같은 이름이 둘이면 되돌릴 수 없습니다.

## 2. 방법 1 — Supabase 백업에서 되돌리기 (유료 플랜에서만)

**무료 플랜에는 이 방법이 없습니다** — 대시보드의 Backups 가 비어 있습니다. 3장으로 가세요.
유료 플랜이라면 가장 먼저 시도합니다. **계정까지 함께 살아나는 유일한 방법**입니다.

1. Supabase 대시보드 → 해당 프로젝트 → **Database → Backups**
2. 되돌릴 시점을 고릅니다
   - 일 단위 백업: 어제 자정 등
   - PITR(유료 플랜): 분 단위로 되돌릴 수 있습니다
3. 복원을 실행합니다. 복원 중에는 시스템이 멈춥니다.
4. 끝나면 **아래 4장 「되살아났는지 확인하기」** 를 그대로 합니다.

⚠️ 복원은 **그 시점 이후의 입력을 전부 없앱니다.** 되돌리기 전에 지금 상태의
전체 스냅샷을 먼저 받아 두세요 — 잘못 되돌렸을 때 돌아올 자리가 됩니다.

## 3. 방법 2 — 전체 스냅샷에서 되살리기

Supabase 프로젝트 자체가 없을 때. **이 길은 실제로 걸어 봤습니다.**

### 3-1. 필요한 것

- 받아 둔 스냅샷 파일 (`비원미래-전체스냅샷-*.json`)
- 이 저장소 (`supabase/migrations/` 와 `scripts/`)
- 빈 Postgres 데이터베이스 하나 (새 Supabase 프로젝트 또는 직접 세운 Postgres)

### 3-2. 빈 구조 만들기

`supabase/migrations/` 의 파일을 **번호 순서대로** 실행합니다.

```bash
for f in supabase/migrations/00*.sql; do
  psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$f" || break
done
psql "$DATABASE_URL" -c "select public.app_schema_version()"   # 64 가 나와야 합니다 (migrations 의 마지막 판)
```

실측: 표 35개가 만들어집니다. 구조는 전적으로 이 저장소에서 나오므로,
git 만 있으면 언제든 다시 세울 수 있습니다.

**그다음 — 운영 DB 에 실행했던 `supabase/proposals/PROPOSAL_*.sql` 을 번호 순서대로 실행합니다.**
운영 DB 는 migrations 뒤에 이 파일들을 실행해 표와 칸이 더 생긴 상태입니다. 이걸 빼먹고 스냅샷을 부으면
그 뒤에 생긴 칸의 값이 들어갈 자리가 없습니다.

```bash
for f in 0066_client_facts 0067_field_schedule 0070_ops_setup 0073_day_close 0074_amend \
         0075_supply_items 0076_snooze_who 0077_schedule_origin 0079_stock_items \
         0083_customer_platform 0087_request_detail 0106_evidence 0108_ax_coach \
         0122_pilot_clients 0123_pilot_start; do
  psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "supabase/proposals/PROPOSAL_$f.sql" || break
done
```

- 어느 파일까지 실행해야 하는지는 **복구 SQL 이 알려 줍니다**(3-3 에서 만든 파일의 맨 위, 그리고 모자라면 3-4 에서 멈추며 이름을 말합니다).
- 스냅샷 파일 안의 `schemaVersion` 이 그때 운영 DB 의 판입니다 — 같은 숫자가 되면 맞게 실행한 것입니다.
- 위 15개가 **표 · 칸을 더하는** 파일입니다(2026-11 기준). 그 밖의 `0072_testdata_rest` · `0127_…_DRYRUN` ·
  `0128_clear_…` · `PROPOSAL_ADDR_pilot` · `FILL_…` · `CHECK_…` 은 자료를 고치거나 확인만 하는 파일입니다. **실행하지 않습니다.**
- 사업계획서 · 설문(0144~0148) · 유지 신호(0151)는 그 기능을 다시 쓸 때 실행합니다(복구 SQL 과는 무관).

> Supabase 대시보드의 SQL Editor 에 파일 내용을 순서대로 붙여 넣어도 같습니다.

### 3-3. 복구 SQL 만들기

```bash
node scripts/restore-from-snapshot.mjs 비원미래-전체스냅샷-20260815-0930.json > restore.sql
```

이 스크립트는 **데이터베이스에 직접 쓰지 않습니다.** SQL 텍스트만 만듭니다.
복구는 되돌릴 수 없는 작업이라, 넣기 전에 사람이 파일을 열어 보게 했습니다.
맨 위에 무엇이 몇 줄 들어가는지, 무엇이 복구되지 않는지 적혀 있습니다.

### 3-4. 붓기

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f restore.sql
```

- **맨 앞에서 구조를 확인합니다.** 스냅샷에 든 표 · 칸이 이 DB 에 하나라도 없으면 **아무것도 바꾸지 않고 멈추고**,
  무엇이 없는지 · 어느 proposals 파일을 먼저 실행해야 하는지 말합니다. 예전에는 이 확인이 없어서, 옛 구조의 DB 에 부으면
  없는 칸의 값이 **말없이 버려진 채 성공**으로 끝났습니다.
  칸이 없어진 것을 알고도 부어야 할 때만 `RESTORE_SKIP_PRECHECK=1 node scripts/restore-from-snapshot.mjs …` 로 이 확인을 끕니다
  (그 칸의 값은 버려지고, SQL 머리말에 그렇게 적힙니다).
- **한 트랜잭션입니다.** 한 줄이라도 안 들어가면 전부 되돌아갑니다 —
  반쯤 복구된 데이터베이스가 가장 위험합니다.
- **대상 표를 먼저 비웁니다.** 되살릴 데이터베이스에만 실행하세요.
- 같은 파일을 **두 번 부어도 결과가 같습니다.** 중간에 끊겼으면 그냥 다시 부으면 됩니다.
- 실측: 321줄에 **0.13초**. 실제 자료(수만 줄) 기준으로도 1분 이내입니다.

### 3-5. 사람 다시 들이기

스냅샷에는 **로그인 계정이 없습니다.** Supabase 의 `auth` 영역에 있어서 이 파일에
담기지 않습니다. 되살린 뒤:

1. Supabase → Authentication → 직원들을 초대(또는 각자 회원가입)
2. 시스템의 **사용자 관리** 화면에서 승인하고 역할을 줍니다
3. 첫 관리자 한 명은 SQL 로 직접 만들어야 합니다:
   ```sql
   update public.profiles set role = 'admin', active = true, approved_at = now()
    where email = '대표님이메일@example.com';
   ```

「누가 넣었는지」는 **이름으로는 남아 있습니다**(`actor_name`). 계정과의 연결만 끊깁니다.

## 4. 되살아났는지 확인하기

되돌린 다음 반드시 합니다. 줄이 들어간 것과 **업무가 되는 것**은 다릅니다.

| 확인 | 어떻게 | 맞는 값 |
| --- | --- | --- |
| 구조 | `select public.app_schema_version()` | 스냅샷 파일의 `schemaVersion` 과 같은 값 |
| 거래처 | 거래처 화면 | 거래처 수가 맞는가 |
| 돈 | 미수금 화면 | **되돌리기 전에 받아 둔 CSV 와 1원까지 같은가** |
| 청구 | 미수금 → 아무 청구나 열기 | 명세서가 그대로 뜨는가 |
| 잠금 | 청구를 지워 보기 | **막혀야** 정상입니다 |
| 기록 | 감사로그 화면 | 예전 기록이 이름과 함께 보이는가 |
| 새 입력 | 수거 하나 입력 → 취소 | 오류 없이 되는가 |

마지막 줄이 중요합니다. **자동 번호**(감사기록의 id 같은 것)를 맞추지 않으면 복구는
성공한 것처럼 보이는데 그 다음 기록 한 줄에서 막힙니다. 복구 SQL 이 이걸 맞추지만,
되돌린 다음 날 아침이 아니라 지금 확인하는 편이 낫습니다.

## 5. 무엇이 되살아나고 무엇이 안 되는가

실제로 되돌려 보고 센 것입니다.

### 되살아납니다 (표 29개 + 나중에 더한 표 7개)

거래처 · 차량 · 수거 · 자재 공급 · 자재 입출고 · 사무실 재고 · 현장 메모 ·
병원 요청 · 요청 처리 결과 · 거래처 문서 · 단가 이력 · Excel 월 실적 ·
매출 직접입력 · 월 운영비 · 휴무일 · **청구 · 입금** · 수거 입력 기록 ·
추가 매출 제안 · 제안 이력 · **감사기록** · AX 실증 설정 · AX 기준값 ·
직원 명부 · 부가세 과세표준 · **소모품 상품 · 소모품 주문 · 주문 품목** · 현장 의견

나중에 더한 표(proposals 를 실행한 DB 에만 있습니다 — 2026-11 부터 스냅샷에 담깁니다):
**병원 문의** · **품목별 사무실 재고** · 자재 품목 구분 · 운영 변화 기록 · 배차 결정 기록 · 추천 노출 기록 · AI 호출 기록

### 파일에 들어 있지만 자동으로 되살아나지 않습니다 (보관용 사본)

스냅샷 파일의 `extras` 안에 내용이 그대로 있습니다. 복구 SQL 은 이 부분을 넣지 않습니다 — 사람이 보고 다시 넣습니다.

| 무엇 | 왜 자동이 아닌가 |
| --- | --- |
| **사업계획서** (현재 내용 · 저장해 둔 판 전부 · 최근 기록 200건) · **사업화 전략/결정** · **설문 응답** | 누가 썼는지 · 누가 확인했는지가 계정에 묶여 있고, 표가 서버 함수로만 열립니다 |
| **하루 마감 기록** · **AX 코치 확인 기록** · **차량 예약** | 「누구의 것」인 칸이 비울 수 없는 칸입니다. 계정이 없는 파일에서는 넣을 수 없습니다 |

### 되살아나지 않습니다

| 무엇 | 왜 | 어떻게 하나 |
| --- | --- | --- |
| **로그인 계정** | Supabase 의 `auth` 영역이라 스냅샷에 못 담습니다 | 3-5 대로 다시 초대 |
| **개발자 요청함** | 요청자 계정이 반드시 있어야 하는 표입니다 | 업무 자료가 아니라 포기합니다 |
| **누가 넣었는지의 계정 연결** | 없는 계정을 가리키면 복구가 통째로 실패합니다 | 이름(`actor_name`)은 남습니다 |

### 정확히 같지 않은 것 — 하나

소수점이 붙은 수는 `1.0` 이 `1` 로 바뀝니다(json 을 거치면서 「소수점 한 자리짜리 1」이라는
구분이 사라집니다). **값은 같습니다.** 영향받는 칸은 차량 톤수 · kg · AX 기준값뿐이고,
**이 시스템의 돈은 전부 정수(원)** 라 금액에는 닿지 않습니다. 실측으로 확인했습니다.

## 6. 어디까지 실제로 해 봤는가

숨기지 않고 적습니다.

| 항목 | 상태 |
| --- | --- |
| 마이그레이션만으로 빈 시스템 세우기 | ✅ 했습니다 (표 35개 · 판 64) |
| 스냅샷 → 복구 SQL → 빈 DB 에 붓기 | ✅ 했습니다 (표 29개 · 364줄) |
| 원본과 복구본 대조 (줄 수 · 금액 · 내용) | ✅ 1원까지 같음 (98개 항목 전부 통과) |
| 나중에 더한 표 7개 — proposals 15개를 실행한 DB 에서 스냅샷 → 복구 → 대조 | ✅ 글자까지 같음 (51개 항목) |
| 옛 구조의 DB 에 부으면 멈추는가 | ✅ 표 · 칸 이름을 말하고 멈춤 · 있던 자료 그대로 |
| 복구 후 새 기록 남기기 · 잠금 동작 | ✅ 확인 |
| 같은 파일 두 번 붓기 | ✅ 결과 같음 |
| **운영 Supabase 프로젝트에서의 백업 복원** | ❌ **아직 안 했습니다** |

마지막 줄이 남은 위험입니다(유료 플랜으로 올린 뒤의 이야기입니다 — 무료 플랜에는 그 백업이 없습니다).
2장(Supabase 백업 복원)은 대시보드에서 하는 일이라 제가 대신 눌러 볼 수 없습니다. 실제로 해 보려면 **운영과 별개의 새 프로젝트**를 하나 만들어
스냅샷을 부어 넣고 복원을 연습하는 방식이 안전합니다. 대표님이 판단하실 일입니다.

## 7. 이 문서를 다시 확인해야 할 때

- 마이그레이션을 새로 추가했을 때 (스키마 판이 올라갔을 때)
- 표를 새로 만들었을 때 → `src/lib/snapshot.ts` 의 `SNAPSHOT_TABLES` 에 한 줄 추가
  (proposals 로 만든 표면 `optional` 에 그 파일 이름을 · 계정에 묶인 표면 `SNAPSHOT_EXTRAS` 에).
  **빠뜨리면 그 표는 백업에 담기지도, 「안 담긴다」고 적히지도 않습니다** — 2026-11 에 그렇게 빠져 있던 표 10개를 찾았습니다.
- 회사가 커져 자료가 크게 늘었을 때 (스냅샷 파일 크기 · 복구 시간)

매번 처음부터 다시 합니다 — 빈 DB 만들기 → 자료 넣기 → 스냅샷 → 복구 → 대조.
