# 실사용 데이터 수집 준비

실제 현장 테스트가 시작되면 **그날부터** 성과 데이터가 쌓여야 합니다.
나중에 소급해서 만들 수 없는 값들이라, 시작 전에 준비를 끝내야 합니다.

이미 구현된 성과측정 기능을 그대로 씁니다. **새로 만들 것은 없습니다.**

---

## 1. 시작 전 반드시 (한 번만)

| # | 항목 | 화면 | 왜 |
|---|---|---|---|
| 1 | **도입 전 기준값 입력** | 설정 → 도입 전 기준값 | 이게 없으면 "얼마나 줄었는지"를 계산할 수 없습니다 |
| 2 | **실증 시작일 지정** | 설정 → 실증 시작일 | 이 날짜 이후만 성과로 집계됩니다 |
| 3 | 시연 모드 해제 확인 | 설정 → 운영 모드 | 실사용 입력이 시연으로 태깅되면 성과에서 빠집니다 |

기준값 5가지 (사용자가 직접 측정해서 입력):

| 기준값 | 어떻게 구하나 |
|---|---|
| 수거 1건당 행정업무 시간 | 지금 방식으로 1건 처리에 걸리는 분 |
| 동일 정보 반복 입력 횟수 | 같은 내용을 몇 군데에 다시 적는지 |
| 월간 문서 작성시간 | 대장·리포트 작성에 쓰는 시간 |
| 월간 누락·재확인 건수 | 빠뜨려서 다시 확인한 횟수 |
| 하루 처리 건수 | 1인 기준 하루 처리량 |

> **추정치를 넣지 마세요.** 심사에서 가장 먼저 묻는 것이 기준값의 출처입니다.
> 입력값의 출처는 화면에 「사용자 입력값」/「시연 기준값」으로 구분 표시됩니다.

## 2. 자동으로 쌓이는 것

수거 완료를 입력하면 아래가 `collection_events` 에 자동으로 남습니다.

| 컬럼 | 내용 | 쓰임 |
|---|---|---|
| `at` | 저장 시각 | 기간별 집계 |
| `actor_id` · `actor_role` | 누가 | 역할별 사용률 |
| `screen` | 어느 화면에서 | 「빠른 완료」 vs 「수거정보 입력」 비교 |
| `input_duration_ms` | **화면 진입 → 저장까지 실제 경과시간** | 행정업무 시간 단축 근거 |
| `amount_kg` · `client_id` | 처리량 | 처리량 추이 |
| `material_ids` · `stock_before` | 자재 동시공급 | 반복 입력 감소 근거 |
| `request_updates` | 자동으로 닫힌 병원 요청 | 자동 연결 건수 |
| `demo_session_id` | 시연 세션 (실사용은 `null`) | **시연/실사용 분리의 핵심** |
| `reverted` | 취소 여부 | 오류·재작업 건수 |

`input_duration_ms` 는 사람이 적는 게 아니라 **시스템이 잰 값**입니다.
그래서 "체감상 빨라졌다"가 아니라 숫자로 말할 수 있습니다.

## 3. 수집 항목별 준비 상태

| 항목 | 상태 | 근거 |
|---|---|---|
| 수거 처리 건수 | 준비됨 | `collection_events` 건수 |
| 입력 시간 | 준비됨 | `input_duration_ms` (시스템 측정) |
| 반복 입력 감소 | 준비됨 | 기준값 대비 자동 연결 건수 |
| 오류·누락 | 준비됨 | `reverted` + 중복 차단 로그 |
| 처리량 | 준비됨 | `amount_kg` 합계 |
| 추천 → 제안 → 수락 → 실제 매출 | 준비됨 | `sales_leads` + `sales_lead_events` |
| **사용자 의견** | **미구현** | 아래 5번 |

## 4. 시연과 실사용이 섞이지 않는 이유

| 층 | 장치 |
|---|---|
| 저장 | 실사용 입력은 `demo_session_id = null`, `origin = 'field'` |
| 집계 | `provenanceOf()` 가 현장/시연 건수를 나눠 셉니다 |
| 표시 | 화면에 「실제 현장 N건 · 시연 N건」이 항상 같이 보입니다 |
| 근거 등급 | 현장 표본 수에 따라 없음 → 초기 → 축적 → 현장 |
| 초기화 | 실사용 모드에서는 시연 초기화 기능이 **동작하지 않습니다** |
| 기간 | 실증 시작일 이전 데이터는 집계에서 빠집니다 |

즉 **시연 숫자가 성과로 둔갑할 수 없는 구조**입니다.
근거 등급이 「현장」이 되기 전에는 화면이 스스로 "표본이 적다"고 밝힙니다.

## 5. 사용자 의견 — 앱 밖에서

현재 앱에는 의견 수집 기능이 없고, **이번에 만들지 않았습니다.**
설문 기능을 붙이는 것보다 초기에는 직접 듣는 편이 훨씬 정확합니다.

권장 방식:

- 실사용 1주차 · 4주차에 역할별로 짧게 인터뷰 (현장 1명, 사무실 1명, 대표)
- 질문은 3개면 충분합니다
  1. 전보다 줄어든 일이 있습니까
  2. 아직 따로 적고 있는 것이 있습니까
  3. 불편해서 안 쓰게 되는 화면이 있습니까
- 답변은 `00_CUSTOMER_PROFILE.md` 8번 인수인계 메모에 기록

> 의견 수집이 반복 업무가 되면 그때 앱에 넣는 것을 검토합니다.

## 6. 테스트 중 점검

| 주기 | 확인 |
|---|---|
| 매일 | 어제 입력 건수 (AX 성과 화면) |
| 주 1회 | 근거 등급이 올라가는지, 실제 현장 건수 |
| 월 1회 | 기준값 대비 개선폭, 전환 퍼널 |

숫자가 안 늘면 **기능 문제가 아니라 사용 문제**일 가능성이 큽니다.
어느 역할이 안 쓰고 있는지부터 확인하세요 (`actor_role` 별 건수).

## 7. 하지 말 것

- 성과가 잘 나오게 하려고 데이터를 만들어 넣지 않습니다.
- 시연 데이터를 실사용으로 옮기지 않습니다.
- 기준값을 나중에 유리하게 고치지 않습니다 (`updatedAt` 이 남습니다).
- 표본이 적은데 대표 성과값을 확정하지 않습니다 — 화면이 자동으로 막습니다.
