# 역할 · 권한 매트릭스

**이 문서는 코드에서 뽑았습니다.** 문서와 코드가 다르면 코드가 맞습니다.

- 화면 접근 — `src/lib/access.ts`
- DB 접근 — `supabase/migrations/0002_rls.sql`, `0006_portal.sql`
- 아래 표는 실제 계정 4개로 PostgREST 를 직접 호출해 확인한 결과입니다 (44건).

---

## 1. 역할 요약

| 역할 | 누구 | 첫 화면 | 한 줄 |
|---|---|---|---|
| `admin` | 대표 · 이사 | `/` 대시보드 | 전부 |
| `office` | 사무실 담당자 | `/` 대시보드 | 운영 전부, 관리자 설정 제외 |
| `field` | 현장 담당자 | `/today` 오늘 일정 | 현장 업무만, 돈 관련 전부 차단 |
| `client` | 병원 담당자 | `/portal` 병원 포털 | 자기 병원만 |

RLS 판정 함수 (`0002_rls.sql`):

| 함수 | 참 |
|---|---|
| `is_admin()` | `admin` |
| `is_staff()` | `admin`, `office` |
| `is_active_user()` | `admin`, `office`, `field` (**`client` 제외**) |
| `is_client_user()` | `client` |
| `auth_client_id()` | 그 계정의 소속 병원 id |

> 핵심: **`client` 는 `is_active_user()` 에 들어가지 않습니다.**
> 그래서 내부 운영 테이블은 정책을 하나하나 막지 않아도 기본적으로 안 보입니다.

## 4. 특히 중요한 네 가지

### 4-1. 권한 상승 차단

`profiles_update_self` 정책은 본인 행을 고칠 때 **`role` 과 `active` 를 현재 값으로 고정**합니다.
이름·글자크기는 바꿀 수 있지만, 스스로 `admin` 이 될 수는 없습니다.
역할 변경은 `is_admin()` 만 가능합니다.

> 확인됨: `field` 계정이 자기 `role` 을 `admin` 으로 PATCH → `403`.

### 4-2. 감사로그는 고칠 수 없습니다

`audit_logs` 에는 **`SELECT` 와 `INSERT` 정책만 있습니다.**
`UPDATE` · `DELETE` 정책이 아예 없어서 **누구도 지우거나 고칠 수 없습니다** (admin 포함).
읽기는 `admin` 만.

> 확인됨: `office` 계정의 `DELETE` → `403 42501`.

### 4-3. 병원 요청 — 병원이 할 수 있는 것과 없는 것

병원 계정의 `INSERT` 정책에는 조건이 셋 붙어 있습니다:

```
client_id = auth_client_id()  AND  source = 'portal'  AND  status = '접수'
```

즉 병원은 **자기 병원 이름으로, 포털을 통해, 접수 상태로만** 요청을 만들 수 있습니다.
남의 병원 이름으로 넣거나, 처음부터 "처리 완료"로 넣을 수 없습니다.

`UPDATE` 는 `is_staff()` 뿐이라 병원은 **자기 요청도 수정할 수 없습니다.**
담당자 회신(`reply`)을 스스로 써넣는 것도 불가능합니다.

> 확인됨: 타 병원 요청 생성 `403` · 타 병원 요청 수정 0행 · 회신 위조 실패.

### 4-4. 영업 제안은 "공유한 것만" 보입니다

`sales_leads_portal_read` 에는 `shared_with_client` 조건이 붙어 있습니다.
담당자가 병원에 전달하기로 한 제안만 병원 화면에 뜹니다.
내부 영업 메모나 예상 매출은 병원에 보이지 않습니다.

## 5. 역할 배정 가이드

| 이런 사람이면 | 역할 |
|---|---|
| 회사 대표 · 이사, 계정을 발급해야 함 | `admin` |
| 배차·청구·병원 응대, 계정 관리는 안 함 | `office` |
| 차 타고 수거 다니는 사람 | `field` |
| 병원 원무과·간호부 담당자 | `client` |

- `admin` 은 **최소 2명** 두세요 (1명이면 그 사람이 못 들어올 때 계정 발급이 막힙니다).
- 현장 담당자에게 `office` 를 주지 마세요. 미수금·매출 데이터가 열립니다.
- 병원 계정은 병원마다 따로 만듭니다 (하나로 여러 병원을 볼 수 없습니다).

## 6. 계정 관리 — 지금 되는 것과 안 되는 것

관리자 화면(설정 → 사용자 계정, `AdminPanels.tsx`)에서:

| 기능 | 상태 |
|---|---|
| 사용자 목록 조회 (이름·이메일·역할·활성) | ○ |
| 역할 변경 | ○ (본인 역할은 변경 불가) |
| 활성 / 비활성 전환 | ○ (비활성 계정은 로그인해도 차단 화면) |
| 변경 이력 감사로그 기록 | ○ (`profile.role`, `profile.active`) |
| **계정 생성** | ✕ — Supabase 대시보드에서 |
| **비밀번호 초기화** | ✕ — Supabase 대시보드 또는 로그인 화면의 재설정 메일 |
| **계정 삭제** | ✕ — Supabase 대시보드에서 |

계정 생성·삭제·비밀번호 초기화는 **Admin API + service_role 키**가 필요합니다.
그 키를 프론트엔드에 넣으면 RLS 가 무력화되므로, 억지로 화면에 만들지 않았습니다.
드물게 하는 작업이라 Supabase 대시보드로 충분합니다.

> 별도 서버(Edge Function 등)를 두면 화면에서도 가능합니다. 필요해지면 그때 검토합니다.
