# 0146 · 제출 예정 사업계획서 — 신보 뉴본펭귄 공동작성 · 검토

신용보증기금 스타트업지점에 낼 「비원미래 신보 뉴본펭귄 사업계획서」를 AX 안에서 함께 쓰고 검토하는 화면입니다.
담당 한 분이 본문을 쓰고, 대표님 · 이사님이 폰에서 읽으며 **확인 표시**와 **수정요청**을 남깁니다.
**수정요청은 문서를 바꾸지 않습니다.** 담당이 보고 반영(또는 까닭을 적고 보류 · 반려)합니다.

> ⚠ 이 저장소는 공개입니다. 이 문서와 코드에는 **회사 숫자 · 계획이 없습니다.**
> 1차 초안은 저장소 밖 SQL 파일로만 전달되고, DB 에만 들어가며, 참여자만 서버 함수로 읽습니다.
> 원본 HWPX · 녹취록 · 재무증빙은 저장소에 올리지 않습니다(`.gitignore` 의 `private/`, `*.hwpx`, `*.hwp`).

## 1. 어디에 있나

| 자리 | 이름 |
|---|---|
| 폰 | 더보기 › 「★ 뉴본펭귄 사전 설문」 바로 아래 **「제출 예정 사업계획서」** |
| PC | 왼쪽 사이드바 › 설문 바로 아래 **「제출 예정 사업계획서 · 열기」** |
| 요청함 | 사용자 피드백 › **「사업계획서 수정요청」** 칸 (`/dev-requests?tab=bizplan`) |
| 주소 | `/bizplan` (`?tab=inbox｜versions｜export｜members`, `?f=항목키` 로 그 항목을 엶) |

메뉴 단추는 대표·관리자에게 늘, 사무실 계정에게는 **참여자로 등록된 경우에만** 보입니다. 현장 · 병원 계정에는 없습니다.
단추를 숨기는 것은 편의일 뿐이고, 여는 것 · 고치는 것은 **서버가** 막습니다(아래 4).

## 2. 화면

- **머리** — 문서 상태(초안 작성 중 → 공동 검토 중 → 수정 중 → 최종 검토 → 제출본 확정), 버전, 작성 진행률(내용이 실제로 들어 있는 칸 / 전체 칸), 검토 완료 · 수정 필요 · 미확인 · 미처리 요청 수, 최종 수정 시각 · 수정자.
- **탭** — 문서 · 요청함 · 기록·버전 · 내보내기 · 참여자(관리할 수 있는 분만).
- **문서 — PC 3칸**: 목차(절마다 작성 수 · 확인 필요 · 요청 수) | 본문(원본 서식 순서 그대로) | 검토 칸(상태 · 출처 · 내 확인 표시 · 수정요청 · 변경 기록).
- **문서 — 폰 3단계**: ① 목차 → ② 본문 → ③ 수정요청. 단계를 바꾸면 단계 띠가 화면 위로 올라와 요약을 다시 내려 보지 않습니다.
- **거르기** — 전체 · 확인 필요 · 수정 요청 있음 · 미작성 · 최종 확인 완료 · 의견 조율 필요.
- 칸마다 상태를 **글자 + 옅은 색**으로 보입니다(색만으로 말하지 않음). 출처 · 기준일 · 사실/추정/계획/미확인 · 「확인할 것」 메모가 함께 보입니다.

## 3. 원본 구조

신보 원본 서식(혁신스타트업용)을 풀어 **순서 · 표 칸 · 단위 · 작성 안내 · 주석을 그대로** 옮겼습니다(`src/lib/bizPlan.ts`).

표지 · 확약 → 1 기업체 현황 … 11 사업 추진계획 → (추가) 대표자 서식 ①②③ → 작성 참고사항 → 별첨(추정매출액 및 고용창출 · 1차년도 소요자금 · [별첨1] 현금 유출입 · [별첨2] 기술개요표) → 기술역량평가 작성요령.

- 21개 절 · 146칸(값을 받는 칸 121 · 원본 고정 문구 5 · 이 시스템에 저장하지 않는 칸 20).
- 표는 칸마다 따로 받습니다(예: 11번 매출전망 = 사업부문 · 예상매출 · 산출근거, 합계 자동).
- 원본 표에 들어 있는 **예시 숫자 · 예시 기간은 값으로 쓰지 않고** 안내 글에만 둡니다.
- 원본이 글자 사이를 띄워 쓴 칸 이름(「대 표 자 명」)은 화면에서 붙여 씁니다(「대표자명」).

- 확약 · 동의 · 서명은 자동으로 처리하지 않습니다.

## 6. 수정요청 흐름

1. 검토하는 분이 항목에서 「수정 요청」 → 유형(사실관계 수정 · 숫자 변경 · 문장 수정 · 내용 추가 · 내용 삭제 · 증빙자료 확인 · 의견 또는 질문 · 최종 확인 요청) · 내용 · (선택) 제안 문장.
   항목 이름 · 그때 내용 · 요청자 · 시각은 자동으로 남습니다.
2. 고치는 요청이면 항목 상태가 「수정 요청 있음」이 됩니다. **내용은 그대로입니다.**
3. 담당이 요청함(또는 그 항목)에서 처리 — 검토 시작 → **제안 반영 · 편집**(바꾸기 전 · 후 비교를 보고 저장하면 요청이 「반영 완료」로 닫히고 기록과 이어짐) / 반영 완료(내용 그대로) / 보류 · 반려(**까닭 필수**).
4. 요청자는 그 항목과 요청함에서 결과(누가 · 언제 · 까닭)를 봅니다.

**확인 표시**는 사람마다 따로입니다(동의 · 수정 의견 있음 · 자료 확인 필요 · 추후 논의). 한 분은 「동의」, 다른 분은 「수정 의견」이면 「의견 조율 필요」로 모입니다.

## 7. 동시에 고칠 때

저장할 때 판 번호(rev)를 들고 갑니다. 창을 연 사이 다른 분이 고쳤으면 서버가 **저장하지 않고** 그분 내용을 돌려줍니다.
편집 창이 두 내용을 나란히 보여 주고, 「그분 내용으로 다시 고치기」 또는 「확인했고 내 내용으로 저장」을 고르게 합니다. 조용히 덮어쓰지 않습니다.
(실시간 공동 편집은 아닙니다. 화면은 앱으로 돌아올 때 서버 내용을 다시 읽습니다.)

## 8. 기록 · 버전

- 항목마다: 바꾸기 전 · 후, 누가 · 언제, 까닭, 연결된 요청, 상태 변화.
- 버전: V0.1 · V0.2 … 그 순간 전체를 통째로 저장. **같은 이름은 거절 — 저장한 버전은 덮어쓰지 않습니다.**
- 제출본 확정: 버전을 「제출본」으로 저장(예: V1.0). 처리 전 수정요청이 있으면 서버가 거절합니다. 확정 뒤 고치면 문서가 「수정 중」이 되고, 확정본은 그대로 남습니다.
- 버전마다 「미리 보기」 · 「지금과 비교」.

## 9. 내보내기

- 원본 순서 그대로, **검토 표시(상태 · 요청 · 확인 · 출처 메모) 없이** 깨끗한 문서.
- 인쇄 · PDF 저장(이 문서만 찍힘) · 전체 복사(원본 서식에 옮겨 적기용) · 자료 내보내기(JSON, 칸 이름 그대로) · 진행 현황(CSV — 이것만 상태가 들어감).
- 제출 전 점검: 처리 전 요청 · 최종 확인 전 칸 · 빈 칸 · 직접 기입 칸 · 「○○ · 확인 필요 · 미정 · (예시)」가 남은 칸(누르면 그 항목으로).

## 10. 켜는 순서 (대표님)

1. Supabase SQL Editor 에서 `supabase/proposals/PROPOSAL_0146_bizplan.sql` 실행 — 마지막 줄 `표 (9) 9 · 함수 (14) 14`.
2. 앱에서 대표 계정으로 `/bizplan` › 참여자 탭 — 담당 계정(편집)과 이사님 계정(검토) 등록.
3. (선택) 1차 초안 SQL(저장소 밖 파일, 따로 전달) 실행 — 아직 아무도 손대지 않은 칸만 채우고, 칸마다 「1차 초안 입력 (V0.1)」 기록과 버전 V0.1 을 남깁니다. 여러 번 실행해도 됩니다.

SQL 실행 전에는 화면이 「아직 서버 준비 전입니다 (PROPOSAL_0146_bizplan.sql 실행 필요)」를 보이고, 가짜 내용을 보이지 않습니다.
끄려면 `src/lib/bizPlan.ts` 의 `BIZPLAN_ENABLED = false`.
