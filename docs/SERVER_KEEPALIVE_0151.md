# 무료 Supabase 로 안전하게 운영하기 — 일시정지 · 유지 신호 · 백업 (0151)

> Supabase 무료 플랜은 두 가지가 다릅니다. **1주일 동안 사용이 없으면 프로젝트가 일시정지**되고,
> **자동 백업이 없습니다.** 이 문서는 그 둘에 대해 무엇을 만들었고, 무엇이 대표님 결정으로 남아 있는지 적습니다.

## 1. 일시정지는 무엇인가

| | |
|---|---|
| 언제 | 지난 1주일 동안 **사용자 DB 활동이 충분하지 않을 때** (공식 문서 — 하루에 요청 몇 번이면 보통 충분) |
| 미리 알림 | 일시정지 약 1주일 전에 Supabase 가 프로젝트 소유자에게 메일을 보냅니다 |
| 멈추면 | 모든 요청이 `540` 으로 돌아옵니다. **자료 · 계정은 그대로** 있습니다 (지워지는 것이 아님) |
| 푸는 법 | Supabase 대시보드 → 그 프로젝트 → **Restore project**. 몇 분 걸립니다 |
| 안 걸리려면 | ① 직원이 앱을 쓴다(그 자체가 DB 활동) ② 유지 신호를 주기적으로 보낸다 ③ 유료(Pro) 플랜 — 일시정지 없음 |

「쓰기」여야 하는 것은 아닙니다. 읽기 요청도 DB 활동입니다. 그래서 「아무거나 넣었다 지우기」는 필요 없습니다.

## 2. 이번에 만든 것

| 무엇 | 어디 | 상태 |
|---|---|---|
| 일시정지 · 응답 없음 안내 | 로그인 화면 · 앱 위쪽 띠 · 병원 화면 | 배포됨. 예전에는 「계정 정보를 찾지 못했습니다 — 계정을 다시 만들어야 합니다」(틀린 안내)가 나왔습니다 |
| 유지 신호 주소 | `/api/keepalive` | 배포됨. 누가 부를 때만 동작합니다 |
| 마지막 신호 기록 | `supabase/proposals/PROPOSAL_0151_keepalive.sql` | **대표님이 실행**(선택). 안 해도 신호는 갑니다 |
| 유지 신호 카드 | 설정 → 서버 점검 → 「서버 유지 신호」 | 배포됨. 관리자만 |
| 전체 스냅샷 알림 | 첫 화면 한 줄 · 설정의 스냅샷 카드 | 배포됨. 관리자만 |
| 스냅샷에 빠져 있던 자료 | 병원 문의 등 표 7개 + 사본 6가지 | 배포됨 (아래 5장) |

### `/api/keepalive` 가 하는 일

- 공개 키(anon)로 DB 함수 `app_ping()` 을 3번 부릅니다. 그 함수가 아직 없으면(PROPOSAL_0151 전) 로그인 전용 함수를
  불러 DB 가 「권한 없음」이라고 **답하게** 합니다 — DB 까지는 닿습니다.
- 업무 자료는 읽지도 쓰지도 않습니다. 새 비밀 값도 없습니다(앱 빌드에 이미 쓰는 공개 주소 · 공개 키).
- 답: `{ ok, state, needs_sql, at }`. 주소 · 키는 답에 없습니다.

| `state` | 뜻 | HTTP |
|---|---|---|
| `ok` | DB 가 신호를 기록했습니다 | 200 |
| `reached` | DB 까지 닿았습니다. 기록 함수가 없어 시각은 안 남았습니다 (`needs_sql: true`) | 200 |
| `paused` | 프로젝트가 일시정지 상태입니다 → Restore project | 503 |
| `down` | DB 가 응답하지 않습니다 | 503 |
| `not_configured` | 배포 서버에 Supabase 주소 · 공개 키 환경변수가 없습니다 | 500 |

### PROPOSAL_0151 이 더하는 것 (지우는 것 없음 · 여러 번 실행해도 됨)

- `app_heartbeat` — 한 줄짜리 표. 누구도 직접 읽거나 고칠 수 없습니다.
- `app_ping()` — 로그인 없이 부를 수 있는 **유일하게 쓰는** 함수. 그 한 줄의 시각 · 횟수만 고치고, **5분에 한 번만** 씁니다.
- `app_heartbeat_status()` — 로그인한 사람이 「마지막 유지 신호」를 읽습니다.
- 끝에 `0151 · 표 1/1 · 함수 2/2 · 신호 1번` 이 나오면 됩니다.

## 3. 대표님이 정하실 것 — 예약 호출

**지금은 사람 손 없이 신호를 보내는 예약이 달려 있지 않습니다.** 사람이 없어도 계속 도는 자동 작업은 대표님이
켜기로 하셨을 때만 다는 것이 맞다고 보아, 만들기만 하고 달지는 않았습니다. 「켜 달라」고 하시면 아래 중 고르신 것을
그대로 추가합니다. 직접 하셔도 됩니다.

직원이 매일 앱을 쓰는 동안에는 예약이 없어도 일시정지되지 않습니다. 예약은 **연휴 · 아무도 안 쓰는 주**를 위한 것입니다.

### 방법 A — Vercel Cron (하루 한 번)

`vercel.json` 에 한 덩어리를 더합니다. Vercel 무료(Hobby) 플랜은 **하루 한 번**까지만 됩니다(더 잦은 식은 배포가 실패).
시각은 ±59분 어긋날 수 있습니다.

```json
"crons": [{ "path": "/api/keepalive", "schedule": "17 21 * * *" }]
```

(UTC 21:17 = 한국 06:17.) 실패해도 알림은 없습니다 — 설정의 유지 신호 카드에서 「며칠째 신호 없음」으로 보입니다.

### 방법 B — GitHub Actions (6시간마다 · 실패하면 메일)

`.github/workflows/keepalive.yml` 을 만듭니다. 실패하면(일시정지 포함) GitHub 가 저장소 소유자에게 메일을 보냅니다.

```yaml
name: keepalive
on:
  schedule:
    - cron: '23 */6 * * *'
  workflow_dispatch:
permissions: {}
jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - name: 유지 신호
        run: |
          for i in 1 2 3; do
            body=$(curl -sS -m 30 "${{ vars.APP_URL || 'https://beonemirae-ops-mvp.vercel.app' }}/api/keepalive" || true)
            echo "$body"
            echo "$body" | grep -q '"ok":true' && exit 0
            sleep 20
          done
          echo "::error::유지 신호 실패 — state 가 paused 이면 Supabase 대시보드에서 Restore project 를 눌러 주세요."
          exit 1
```

주의: GitHub 는 **60일 동안 저장소에 변화가 없으면** 예약 작업을 스스로 끕니다(공개 저장소). 그때는 Actions 탭에서 다시 켭니다.

A 와 B 를 함께 켜도 됩니다(서로 다른 곳에서 부르므로 한쪽이 멈춰도 다른 쪽이 남습니다). DB 쪽은 5분에 한 번만 쓰이므로 겹쳐도 부담이 없습니다.

### 방법 C — 유료(Pro) 플랜

일시정지가 없고 일 단위 자동 백업이 생깁니다. 신호도 예약도 필요 없어집니다.

## 4. 확인하는 법

1. 주소창에 `https://(운영 주소)/api/keepalive` → `{"ok":true,"state":"ok",...}` (PROPOSAL_0151 전에는 `"state":"reached","needs_sql":true`)
2. 설정 → 서버 점검 → 「서버 유지 신호」 카드
   - 「지금 유지 신호 보내기」 → 「유지 신호를 보냈습니다 — DB 가 기록했습니다」
   - 예약이 켜져 있으면 **마지막 유지 신호 시각이 매일 바뀝니다.** 사흘 넘게 그대로면 카드가 「n일째 유지 신호가 없습니다」라고 알립니다.
   - 이 카드를 여는 것만으로는 신호가 가지 않습니다(그래야 저 시각이 예약이 실제로 돌았는지를 말해 줍니다).

## 5. 백업 — 무료 플랜에는 자동 백업이 없습니다

설정 화면의 **전체 스냅샷이 유일한 백업**입니다. 이번에 고친 것:

- **마지막으로 받은 날** — 받을 때 감사기록에 한 줄을 남기고, 스냅샷 카드에 「마지막으로 받은 날 … (n일 전 · 누구)」를 보여 줍니다.
  30일이 지났거나 · 받은 기록이 없거나 · 마지막 것이 반쪽이면 **첫 화면에 한 줄**이 뜹니다(관리자만).
- **빠져 있던 표 7개** — 병원 문의 · 품목별 사무실 재고 · 자재 품목 구분 · 운영 변화 기록 · 배차 결정 기록 · 추천 노출 기록 · AI 호출 기록.
  migrations 가 아니라 proposals 로 더한 표라 스냅샷 목록에 없었고, 「담기지 않는다」고 적혀 있지도 않았습니다. 이제 담기고 되살아납니다.
- **보관용 사본 6가지** — 사업계획서 · 사업화 전략/결정 · 설문 응답(서버 함수로만 열리는 자료)과
  하루 마감 · AX 코치 확인 · 차량 예약(계정에 묶인 표). 파일 안에 내용이 그대로 들어가지만 **복구 SQL 로 자동으로 되살아나지는 않습니다.**
  사업계획서는 받는 계정이 참여자일 때만 담깁니다 — 못 담으면 화면과 파일이 그렇게 말합니다.
- **복구 SQL 의 구조 확인** — 운영 DB 는 migrations 뒤에 proposals 를 여러 개 실행한 상태입니다. 예전 절차대로 migrations 만 돌린
  빈 DB 에 부으면, 그 뒤에 생긴 칸의 값이 **말없이 버려진 채 「성공」**으로 끝났습니다. 이제 맨 앞에서 표 · 칸을 확인하고,
  모자라면 아무것도 바꾸지 않고 멈춥니다(무엇이 없는지 · 어느 파일을 먼저 실행해야 하는지 말합니다).

절차는 `docs/RESTORE.md`.

## 7. 한계 — 숨기지 않고

- 유지 신호는 Supabase 가 **보장하는 기능이 아닙니다.** 「사용자 DB 활동이 있으면 일시정지하지 않는다」는 정책에 기대는 것이라,
  정책이 바뀌면 효과가 달라질 수 있습니다. 일시정지 전 알림 메일을 꼭 확인해 주세요. 확실한 것은 유료 플랜뿐입니다.
- 예약 호출은 아직 켜져 있지 않습니다(3장).
- 운영 Supabase 에서 실제로 일시정지 → 복원을 해 본 적은 없습니다. 화면 안내는 가짜 540 응답으로 검사했습니다.
- 보관용 사본은 자동으로 되살아나지 않습니다. 사업계획서 기록은 최근 200건까지 담깁니다(저장해 둔 판은 전부).
