# 0147 · 사업계획서 V2 — 동의와 문장 판 번호 · 제출 전 점검 · 운영 적용 안내

0146(공동작성 · 검토, [BIZPLAN_0146.md](BIZPLAN_0146.md))을 그대로 두고, 실사용 전에 꼭 필요한 것만 더했습니다.
회사 숫자 · 계획은 이 문서와 코드에 없습니다(초안은 저장소 밖 SQL).

## 1. 동의는 「그때 문장」에 붙습니다

**문제** — 0146 에서는 이사님이 어떤 문장에 「동의」한 뒤 담당이 그 문장을 고쳐도, 동의가 새 문장에 그대로 붙어 보였습니다.

**지금**
- 항목마다 **내용 판 번호**(`content_rev`)가 있습니다. 내용(value)이 바뀔 때만 1씩 오르고, 상태 · 근거 · 수정요청 접수로는 오르지 않습니다. 표 안 숫자 한 칸만 바뀌어도 오릅니다.
- 확인 표시(동의 · 수정 의견 있음 · 자료 확인 필요 · 추후 논의)는 **표시한 순간의 판 번호와 그때 문장**을 함께 저장합니다.
- 담당이 내용을 고치면 기존 표시는 **지우지 않고** 「변경 전 문장에 대한 표시」로 남고, 그 항목은 **「재확인 필요」** 가 됩니다.
  - 카드 · 목차 · 머리(「재확인 필요 N항목」) · 거르기 「재확인 필요」에 보입니다.
  - 검토 칸에 「내가 표시한 문장 ↔ 지금 문장」 비교가 나오고, 다시 표시하면 **새 판에 대한 표시가 따로** 남습니다. 두 번의 동의가 모두 기록에 남습니다.
- 확인 표시는 **지금 화면에 보이는 판 번호**를 들고 가야 저장됩니다. 그사이 담당이 고쳤으면 서버가 거절(HTTP 409)하고, 화면이 새 문장을 다시 읽어 보여 줍니다. 보지 않은 문장에 동의가 붙지 않습니다.
- 내용을 고치는 저장은 「최종 확인 완료」를 그대로 둘 수 없습니다 → 서버가 「수정 반영 완료」로 바꾸고 기록에 까닭을 남깁니다.
- 판 번호 없이 부르는 예전 모양(앱을 새로 고치지 않은 화면)은 서버가 받지 않습니다 — 「앱을 새로 고쳐 주세요」.

**이미 있던 기록** — 0147 을 실행하면, 이미 있던 확인 표시마다 「표시한 시각까지 내용이 바뀐 기록 수」로 판 번호를, 그 시각의 마지막 내용으로 그때 문장을 채웁니다(기록 표 `bizplan_revisions` 의 시각 기준). 지우거나 고치는 기록은 없습니다. 다시 실행해도 결과가 같습니다.

## 2. 제출본 확정 전 점검

제출본은 **「제출 전 점검」을 거쳐서만** 확정합니다(`bizplan_submit`). 판단은 서버(`bizplan_preflight`)가 합니다.

| 단계 | 무엇 | 확정 |
|---|---|---|
| 차단 | 필수 칸 누락 · 처리 전 수정요청 · 자금소요 합계(A) ≠ 조달 합계(B) | **불가** — 고쳐야 함 |
| 확인 | 재확인 필요 · 최종 확인 전 재무 · 인원 숫자 · 최종 확인 전 중요 사업계획 · 근거 「미확인」 · 근거는 추정/계획인데 글에 예상 · 목표 표시 없음(실적처럼 읽힘) · 「미정 · 미확정 · 추후 · 예시 · ○○ · 확인 필요」 등이 남음 · 작성기간 불일치(1차년도 = 접수월 다음 달부터) · 11번 매출전망 ↔ 별첨 추정매출액 ↔ 품목별 합계 불일치 · 보증신청 금액 > 금융차입 · 별첨 소요자금 ≠ 9번 · 「해당 시 작성」 칸 비어 있음 | 담당이 항목을 확인하고 **까닭(10자 이상)을 적어 예외 승인**하면 가능 |
| 안내 | 제출 직전 원본에 직접 적는 칸(주민번호 · 연락처 · 자산 · 계좌 · 입금동의 · 서명) · 작성일 | 영향 없음 |

- 빈칸을 모두 오류로 보지 않습니다. 칸을 **필수 / 해당 시 작성 / 선택**으로 나눴습니다(서버 `bizplan_rules`). 팩스 · 홈페이지 · 생산방식 · 추가 대표자 서식은 선택입니다. 별첨(리틀펭귄 · 퍼스트펭귄 · Pre-ICON 보증용)은 모두 비어 있으면 「대상 보증인지 확인」 한 줄만 나옵니다.
- 예외 승인한 까닭 · 점검 결과 · 승인자는 **제출본 버전에 함께** 남고(고칠 수 없음), 기록 · 버전 탭에 보입니다.
- 화면: 기록·버전 탭 › 「제출본으로 확정」 → 점검 결과(차단 · 확인 · 안내, 누르면 그 항목으로) → 확인 항목이 있으면 「검토했고 예외로 확정」 + 까닭. 내보내기 탭에도 같은 점검이 보입니다.
- 접수월은 「작성일」 칸, 없으면 오늘(한국 시각) 기준입니다.

## 3. 참여자 관리는 대표 · 관리자만

0146 에서는 담당(editor)도 참여자를 등록 · 변경할 수 있었습니다. 0147 부터는 **대표 · 관리자(admin) 계정만** 할 수 있습니다. 담당은 문서를 고치고 요청을 처리하지만, 누가 볼 수 있는지는 정하지 못합니다(외부 담당이 접근 권한을 넓힐 수 없게).

## 5. 초안 V0.2 (저장소 밖)

`private/bizplan_seed.mjs` → `private/bizplan_seed_v0_2.sql` (대표님께만 따로 전달 · 커밋 안 함).
- 빈 칸 → 채움(「초안 보완 입력 (V0.2)」 기록 · 판 번호 +1).

## 8. 외부 사업계획 담당의 권한 (최소 권한 검토)

- 지금 참여자는 **대표·관리자 · 사무실 계정만** 될 수 있습니다. 외부 담당에게 사무실(office) 계정을 주면, 사업계획서 외에 거래처 · 수거 · 청구 · 미수금 · 매출 등 **사무실이 보는 운영 정보를 모두** 볼 수 있습니다(RLS 의 `is_staff()` = 관리자 · 사무실).
- 0147 로 담당은 **참여자 관리를 못 하게** 했습니다(접근 범위를 스스로 넓히지 못함).
- **권장(대표님 승인 필요)**: 사업계획서 전용 역할을 하나 더하는 것. 확인한 내용 —
  - 기존 정책 · 함수는 역할을 「허용 목록」으로 검사합니다(`is_staff()` · `is_active_user()` · `is_client_user()` 모두 `in (...)` / `=`). 예외였던 `products_read`(`auth_role() is not null`)는 0063 에서 이미 바뀌었습니다. 따라서 새 역할은 **기본으로 아무 운영 정보도 못 봅니다.**
