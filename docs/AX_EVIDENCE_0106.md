# 0106 — AX 성과 계산: 무엇을 세고, 무엇을 세지 않는가

> 목적: 실제 직원과 병원이 쉽게 쓰는 시스템으로 개선하고, AX 도입 효과를 **신뢰할 수 있는
> 데이터**로 증명한다. 이 문서는 이번 작업에서 바로잡은 계산과, 새로 쌓이는 증거, 아직 확인하지
> 못한 것을 사실대로 적습니다. 「앞으로 이렇게 하면 됩니다」가 아니라 **지금 코드가 이렇게
> 합니다**입니다.

## 0. 최신 사업 상황 — 출처와 확인 상태를 같이 둡니다

`src/lib/companyFacts.ts` 에 값과 상태를 함께 둡니다. 화면(실증 준비 상태 · 성과 화면의
성장 사슬)과 브리핑 인쇄가 같은 파일을 읽습니다.

| 항목 | 값 | 상태 |
|---|---|---|

매출 성장 전체를 AX 효과로 적지 않습니다. 성장은 회사가 한 일이고, AX 가 바꾼 것은
측정 결과 칸이 말하는 만큼입니다.

## 1. 표본 — 한 곳에서 정합니다 (`src/lib/evidenceBase.ts`)

이전 검토에서 재현된 불일치: 취소된 수거 30건만 있을 때 준비도 「준비됨」, 성과 「유효 표본 0」.
두 화면이 다른 기준으로 셌기 때문입니다. 이제 `evidenceSample()` 하나가 분류합니다.

| 분류 | 뜻 | 세는가 |
|---|---|---|
| field | 실제 현장 입력 | ✔ |
| demo | 시연 세션 기록 | 따로 표시, 성과에는 ✗ |
| practice | 실증 시작일 **이전** 입력 (연습·시험) | ✗ (건수만 알림) |
| reverted | 완료 취소 | ✗ (「취소 후 재입력」 지표에만) |
| migrated / seed 일정 | 이관된 과거 실적 · 시드 | 커버리지 분모에서도 ✗ |

「시연 표식이 없다」는 이유만으로 현장이라 단정하지 않습니다 — 실증 시작일이 없으면 연습을
가르지 못한다는 사실(`startUnset`)과, 출처가 적히지 않은 일정 수(`originUnknown`)를 같이 냅니다.

**폭(breadth)** — 건수 외에 입력한 날 수 · 병원 수 · 기사 수 · 입력 커버리지(완료 일정 중 시스템
입력 비율) · 누락률(완료 일정 중 수거량·완료시각 빈 비율)을 냅니다. 준비 상태·성과·브리핑이
`breadthLine()` 한 문장을 같이 씁니다.

## 2. 바로잡은 계산 (요구 A~F)

### A. 서로 다른 업무 범위를 견주지 않습니다
- 예전: 도입 전 「배차·일정·엑셀 정리 전체 사무시간 ÷ 방문 수」 vs 도입 후 「입력 화면 진입→저장」 → 개선율.
- 지금: `inputTime` (수거 1건 입력 소요시간)은 **측정값만** (`no-comparable`, 개선율 없음).
  `adminTime` (수거 1건 사무업무 시간)은 도입 후 **같은 세 가지 일**을 다시 조사한 값
  (`performance_baselines.after_*`, 설정 → 도입 후 같은 범위 조사값)이 있을 때만 견줍니다.
- 출처를 넷으로 가릅니다: 업무 조사 응답 · 직접 입력(추정) · 시스템 자동 측정 · 증빙 대조.

### B. 「반복 입력 1회」를 확정 감소율로 쓰지 않습니다
- 시스템 안 1회는 구조값입니다. 도입 후 값은 `1 + (엑셀·카톡에 다시 적었다고 답한 건수 ÷ 현장
  수거 입력 건수)`, **응답한 날이 5일 이상**일 때만 냅니다.
- 응답은 첫 화면의 하루 한 줄(「오늘 엑셀·카톡에 다시 적은 것이 있었나요?」)로 쌓입니다.
  저장은 기존 `dev_requests` 를 재사용합니다(새 표 없음). 안 답한 날은 「없음」이 아니라 「모름」입니다.

### C. 취소·시연·연습·기간 제외 기준을 통일했습니다
- 준비 상태 · 성과 · 브리핑 인쇄가 `evidenceSample()` 하나를 씁니다. `check_evidence0106 ①` 이
  「취소만 30건 → 두 화면 모두 현장 0건」을 확인합니다.
- 실제 업무일(`schedules.date`)과 입력일(`completed_at` 한국시간)은 당일 입력률에서 갈라 씁니다.

### D. 30건은 자동 실증 완료 기준이 아닙니다
- `BREADTH_RULE` = 현장 30건 · 입력한 날 14일 · 병원 5곳 · 기사 2명 · 커버리지 80% — **내부 표시
  기준**이며 공식 기준·통계적 대표성이 아니라고 화면과 인쇄물에 적습니다.
- 「대표 성과값」(강조)은 같은 범위 개선율 + 현장 표본 + 시연 미혼합 + 폭 충족 + 복합 개선 아님을
  전부 만족할 때만입니다. 하루에 한 사람이 넣은 32건은 `partial` 입니다 (`check_ready96 ②`).

### E. 추천과 매출의 연결
- 되짚어 계산한 값은 이제 「주문 품목과 추천 규칙의 **일치**」라고 부릅니다 — 병원이 봤다는 증거가
  아니라고 근거에 적습니다.
- 실제 노출은 `recommendation_views` (판 106)에 그 순간 남깁니다: 병원 화면에 추천이 떠 있던
  시각·품목·규칙 판(`NEEDS_RULE_VERSION`). 주문에 담기면 `ordered` 행이 주문 id 를 가리킵니다.
  「노출 뒤 채택」만 채택이며, 노출 전 주문은 채택이 아닙니다. 과거 노출은 소급 생성하지 않습니다.

### F. 지표 이름과 계산 대상
- 「누락·재확인 건수」 → 「완료 취소 후 재입력 건수」(측정값만; 도입 전 조사값은 다른 범위라 견주지 않음).
- 「두 번 이상 쓴 병원」 옆에 「**2주 이상에 걸쳐** 쓴 병원」(ISO 주 기준)을 따로 냅니다.
- 매출(전달 완료) · 청구 확정 · 입금 완료 · 판매 매출총이익(매출−원가)을 다른 키로 두고, 운영비 반영
  이익은 여기 없다고 적습니다(통계 → 경영 요약).
- 직원이 대신 접수한 전화·카톡 요청이 0건이면 포털 비율을 내지 않습니다 — 100% 는 대개 「나머지를
  안 적은 것」입니다.
- 도입 전→현재 표에 나빠질 수 있는 지표(다녀오기 전 입력 · 접수→처리 시간 · 방문당 운영비)를 같은
  기준으로 올립니다.

## 4. 차량·거점 변화와 AX 효과 분리 (`src/lib/opsChanges.ts`)

`ops_changes` 에 종류(AX 시작 · 기능 · 차량 · 인력 · 거점 · 계약 · 단가)와 상태(계획/적용),
적용일을 적습니다. 계획은 계획으로 남고 운영 데이터를 바꾸지 않습니다. 성과 비교 구간에
**적용된** 차량·인력·거점·계약·단가 변화가 겹치면 개선율에 「AX 단독 효과 분리 불가 · 복합
개선」이 붙고 강조되지 않습니다. 표가 없으면 「변화 기록 없음(모름)」이라고 말하고 「변화 없음」이라
하지 않습니다. 「서울 소각장 두 곳」 같은 전언은 고정 데이터로 넣지 않았습니다.

## 5. 배차 · AI

- 배차 화면: 배열 순서로 만들던 「정비 예정 / 검사 예정」 가짜 상태를 지웠습니다. 아는 것은 「오늘
  운행 / 오늘 일정 없음」뿐입니다. 제안은 「규칙 기반 · AI 아님」으로 표시하고, 담당자가 이대로
  적용 · 수정 · 적용 안 함과 이유를 남깁니다(판 106). 결과는 그날 완료 일정으로 셉니다.
- AI 요청 정리: 서버 함수 코드와 배포 절차는 있으나 **키·배포 없음**. 고객 요청 회신 창에 「AI 로
  요청 정리」를 붙였고, 호출 한 건마다 `ai_calls` 에 입력·결과·성공/실패·처리시간·담당자 수정 여부를
  남깁니다. 키가 없으면 서버가 503 을 주고 그 실패가 그대로 적힙니다. 가짜 초안을 만들지 않습니다.
  AI 연결 개수는 성과 목표가 아니라고 준비 상태 화면에 적었습니다.

## 6. 화면에서 바뀐 것 (사용자가 체감하는 것)

- 첫 화면(사무실·관리자): 「오늘 엑셀·카톡에 다시 적은 것이 있었나요?」 한 줄. 답하면 사라집니다.
- 거래처 정리 도우미: 빈칸마다 **어떤 업무가 막히는지** 적습니다. 담당 기사 배정을 쓰기 시작한 뒤부터
  「담당 기사 없음 → 모든 기사에게 보임」도 셉니다.
- 고객 요청: 상태 버튼·회신 저장의 결과(저장됨/실패)가 그 자리에 보입니다. 실패하면 창이 닫히지 않습니다.
- 성과 화면: 홍보 문장 대신 표본의 폭 한 줄 · 복합 개선 여부 · 「측정값만 / 측정 완료」 구분 ·
  성장 → 병목 → AX → 측정 → 투자 → 목표 사슬(줄마다 출처 배지).
- 실증 준비 상태(구 심사 준비도): 시스템이 확인하는 것 / 사람이 서류로 확인하는 것으로 나눔.
  합격 점검표처럼 읽히는 문구와 자동검사 수 자랑을 뺐습니다.
- 사무실 계정에는 관리자 전용 화면으로 가는 막다른 단추를 그리지 않습니다.
- 메뉴: 「심사 준비도」 → 「실증 준비 상태」, 「통장 대사」 → 「통장 입금 대사」, 배차 화면 제목 「배차·경로」.
- 오늘 업무 마감: 「운행 기록 적기(선택)」 — 출발·도착 계기판, 처리시설 대기 분, 방문 횟수.
  마감 여부 조회 실패를 삼키지 않고 「확인하지 못했습니다 · 다시 확인」을 보여 줍니다.
- 지어낸 참고치(월평균 목표 105톤 · 월평균 4~5회)와 낡은 문구(「Supabase 연동은 개발 예정」,
  「공휴일은 아직 반영하지 않습니다」, 실운영의 「시연 계속하기」)를 지웠습니다.

## 7. 운영 환경에서 아직 확인하지 못한 것

- `PROPOSAL_0106_evidence.sql` 실행 전에는 운영 변화 기록 · 추천 노출 · 배차 결정 · 마감 계기판 ·
  도입 후 조사값 · AI 호출 기록이 쌓이지 않습니다. 화면은 표가 없다고 말합니다.
- AI 요청 정리는 키 발급 + `supabase functions deploy ai-triage` 뒤에야 실제 호출됩니다.
- 실계정에서 엑셀 확인 응답이 5일 이상 쌓여야 「다시 적는 횟수」가 나옵니다.
- 도입 후 같은 범위 조사는 운영이사가 답해 주셔야 합니다.
- 운영 DB 의 실제 판 번호는 이 작업 환경에서 확인하지 못했습니다 (0106 SQL 첫 블록이 87 미만이면 멈춥니다).
